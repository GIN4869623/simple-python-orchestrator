# 开发总路线

本文用于回答三个问题：项目现在能做什么、应该从哪里读代码、下一步如何推进。
启动命令和目录用途见 [README](../README.md)。

## 一、当前做到哪一步

意图识别和任务编排已拆到不同目录、不同服务进程：

- `intent/`：默认端口 `18003`，只负责分析意图与识别缺失信息。
- `orchestration/`：默认端口 `18002`，保留前端入口、请求分流和执行调度。

编排服务通过 HTTP 调用意图服务，然后选择处理路径：

```text
用户请求
    ↓
意图识别：理解目标、提取参数、识别缺失信息
    ├─ 信息不足 → 返回澄清问题，等待补充后重新提交
    ├─ 明确单一任务 → 直接调用专业智能体
    ├─ 已有标准步骤 → 执行固定业务流程
    └─ 需要动态拆解 → 编排智能体规划、调度、评估与调整
```

| 路径 | 当前例子 | 谁决定执行步骤 |
| --- | --- | --- |
| `direct` | 知识问答、查询设备清单和状态、USRP 专属只读问答 | 入口匹配一个明确的业务调用；专业智能体自行完成内部工作 |
| `fixed_workflow` | 单一 USRP 操作：查询操作指导和设备，再执行硬件任务 | 已定义的固定流程 |
| `orchestrated` | 需要动态拆分任务，或根据中间结果调整后续任务 | Planner 生成计划，编排器调度并根据结果继续、重试或重新规划 |

意图服务默认使用 Ollama 识别意图。直接调用和固定流程不会额外调用模型生成计划或复盘；
业务智能体内部是否调用模型，由各自实现决定。
`./serve-intent --backend fixed` 配合 `./serve-orchestrator --planner fixed` 可以离线联调两个服务，
不代表完整的自然语言理解能力。仅调试代码时也可使用 `--local-intent`，默认服务运行仍通过 HTTP 分离。

当前支持的执行目标是知识智能体、网络监管智能体和 USRP 智能体。
知识服务已有专用 HTTP 适配器；其他目标可使用 Fake 或已有的远程适配器。
本项目负责调用这些服务，不实现它们内部的知识检索、设备工具或专业任务规划。

## 二、先把主流程读明白

建议按下面顺序阅读，每一步都用一个具体请求追踪数据的变化。

| 顺序 | 代码 | 要弄清楚的问题 |
| --- | --- | --- |
| 1 | [models.py](../src/simple_orchestrator/models.py)、[ports.py](../src/simple_orchestrator/ports.py) | 意图、任务、返回结果分别是什么？组件之间依赖哪些接口？ |
| 2 | [orchestration/main.py](../src/simple_orchestrator/orchestration/main.py)、[orchestration/api.py](../src/simple_orchestrator/orchestration/api.py) | CLI 和 HTTP 如何读取配置、组装组件、提交请求和返回结果？ |
| 3 | [intent/service.py](../src/simple_orchestrator/intent/service.py)、[intent/client.py](../src/simple_orchestrator/intent/client.py)、[intent/agent.py](../src/simple_orchestrator/intent/agent.py) | 如何识别目标、参数和缺参？`handling_mode` 如何表达建议的处理路径？ |
| 4 | [orchestration/router.py](../src/simple_orchestrator/orchestration/router.py) | 如何先处理澄清，再选择直接调用、固定流程或动态编排？ |
| 5 | [orchestration/workflows.py](../src/simple_orchestrator/orchestration/workflows.py) | 明确任务如何绑定执行目标？固定 USRP 流程如何定义？ |
| 6 | [orchestration/execution.py](../src/simple_orchestrator/orchestration/execution.py) | 如何执行任务、等待依赖、保存结果、有限重试，以及阻止前置条件失败后的硬件操作？ |
| 7 | [orchestration/graph.py](../src/simple_orchestrator/orchestration/graph.py)、[orchestration/planner.py](../src/simple_orchestrator/orchestration/planner.py) | 动态计划如何生成？批次复盘怎样触发继续、停止或重新规划？ |
| 8 | [tests/](../tests/) | 上述行为有哪些可重复验证的例子？ |

先读懂直接调用，再读固定流程，最后读动态编排。旧的 `orchestration/serial.py` 只用于串行实现对照，
不作为当前主流程的起点。

阅读完成后，应能解释这些边界：

- 意图识别回答“用户要什么”，不生成 Task，也不执行任务。
- 编排智能体只处理需要动态规划的请求，不是所有业务的必经步骤。
- 一个固定流程可以调用多个智能体；参与数量不决定是否需要动态编排。
- `WorkflowExecutor` 是共用执行层，不负责理解意图或调用模型制定计划。
- 直接和固定路径按业务返回状态处理结果，不额外做模型语义评估，失败耗尽重试后停止。
- `failed`、`rejected`、`unknown` 含义不同，物理结果未知不能当作未执行而盲目重试。

## 三、用三个场景验证理解

### 场景 1：明确任务直接执行

请求：“查询有哪些可用设备”。

追踪 `RequestRouter → IntentHttpClient → 意图服务 → 返回意图 → DeviceManager`，检查结果中的 `handling_mode` 为 `direct`，
并确认没有调用 Planner 生成计划或进行模型复盘。
对应测试：[test_request_router.py](../tests/test_request_router.py)、[test_intent_service.py](../tests/test_intent_service.py)。

### 场景 2：标准流程执行硬件任务

请求：“使用 USRP 以中心频率 2.4GHz、采样率 1MHz、增益 10dB，发射 QPSK 信号 5 秒”。

追踪固定流程中的操作指导查询、设备查询和 USRP 执行。确认前两项成功后才进入物理任务，
并分别观察无设备、明确拒绝、物理结果未知时的停止行为。
对应测试：[test_request_router.py](../tests/test_request_router.py)、[test_graph_orchestrator.py](../tests/test_graph_orchestrator.py)。

当前固定流程沿用了已有的 Skill 前置检查。专用知识 HTTP 接口只提供问答，
尚不能代替 Skill 索引和读取接口，因此接上真实知识问答服务不等于硬件流程已联通。
远程 USRP 物理执行仍默认拒绝。

### 场景 3：需要动态规划

使用测试中明确标记为 `orchestrated` 的意图，追踪上游意图如何直接传入编排器，
再观察任务拆分、依赖、批次结果和重新规划。
确认意图只识别一次，重新规划保留成功结果，新任务使用新的 ID。
对应测试：[test_request_router.py](../tests/test_request_router.py)、[test_graph_orchestrator.py](../tests/test_graph_orchestrator.py)、[test_planner.py](../tests/test_planner.py)。

实际自然语言请求如何分流取决于意图模型。复杂请求评测属于后续开发工作，
不能仅凭一句示例请求就认为模型一定选对路径。

## 四、接下来按什么顺序开发

以下是建议推进顺序。每一步先明确输入、输出和完成条件，再改代码。

### 1. 验证意图识别和三条路径

整理实际业务请求，覆盖直接问答、设备查询、固定操作、动态协作、缺参和不支持的请求。
为每条请求记录期望路径、必要参数和预期执行目标。

完成条件：明确任务稳定绕过动态规划；复杂任务不会被直接路径遗漏需求；
信息不足时能提出有针对性的补充问题。

### 2. 接通真实专业智能体

先完成只读能力的接口联调，再推进有副作用的操作。主要代码入口是
`knowledge_http.py`、`remote.py`、`tcp_transport.py` 和 `task_messages.py`。
远程地址由可信配置绑定，不由模型生成。

完成条件：成功、失败、拒绝、超时和格式异常均可追踪；完整业务结果得到保留；
重试和未知状态的处理经过验证。开放真实硬件前，还需要远端支持幂等标识、执行状态查询和取消等能力。

### 3. 后续建立并接入 Agent Registry

你后续建立能力仓库时，先明确每个智能体的能力、必要输入、输出、状态和调用地址如何表达，
再接到意图识别后的能力匹配与执行目标选择环节。

当前 `agents/` 中的 JSON 只是描述草稿，没有被加载。
`agent_registry.py` 中已有默认关闭的内存注册表，可用于研究匹配和校验，
但它不提供在线发现或动态节点注册。

完成条件：能力选择来自统一描述；不可用或不匹配的目标不会被选中；
规划和实际调用使用一致的能力约束。

### 4. 用实际复杂业务完善动态编排

在清晰业务继续走直接或固定路径的前提下，再验证真正需要动态规划的业务，
重点检查任务覆盖、依赖关系、结果验收、失败后的替代方案，以及重新规划是否重复执行已完成任务。

完成条件：用业务结果证明动态编排解决了固定流程无法表达的问题，
并为关键成功和失败路径保留可重复的测试。

### 5. 按业务需要增加会话和运行管理

需要连续澄清、长任务或恢复执行时，再加入会话上下文、持久化、checkpoint、取消与进度事件。

当前 HTTP 支持后台提交和轮询，但执行记录只保存在内存中；
补充信息后重新提交属于一次新运行，不是恢复旧任务。

完成条件：重启、断线或重复提交时能确定任务是否已执行，并避免重复产生物理操作。

## 五、开发时使用哪些入口

启动方式见 [README](../README.md)。模型、服务地址和认证从 `.env` 或 CLI 参数读取，
完整参数可用 `./run --help` 查看，配置模板见 [.env.example](../.env.example)。

| 需要做什么 | 当前入口 |
| --- | --- |
| 本地 CLI 演示 | `./run "查询有哪些可用设备" --local-intent --planner fixed --fake-outcome succeeded` |
| 启动意图识别服务 | `./serve-intent`，默认 `18003`；`POST /api/intent/analyze` 返回结构化意图 |
| 启动编排 HTTP 服务 | `./serve-orchestrator` 或 `./serve`，默认 `18002`；需要配置 `ORCHESTRATOR_API_TOKEN` |
| 同步提交任务 | `POST /api/orchestrator/run`，请求体为 `{"request": "任务文本"}` |
| 后台提交与查询 | `POST /api/orchestrator/runs`，随后 `GET /api/orchestrator/runs/<request_id>` |
| 查看服务状态 | `GET /health` |
| 运行自动化测试 | `.venv/bin/python -m unittest discover -s tests -q` |

编排 HTTP 入口要求 `Authorization: Bearer <ORCHESTRATOR_API_TOKEN>`。
意图服务使用 `INTENT_API_TOKEN`；未单独配置时复用 `ORCHESTRATOR_API_TOKEN`。
本机 `.env` 已将两个服务配置为绑定局域网地址 `192.168.1.106`，外部程序可分别访问
`http://192.168.1.106:18002` 和 `http://192.168.1.106:18003`。
`INTENT_SERVICE_URL` 配置为 `http://192.168.1.106:18003`，与意图服务的监听地址一致。
迁移机器或 IP 变化时同步调整这三个地址配置；未配置时，代码的回退监听地址仍是 `127.0.0.1`。
两个进程可以分别设置模型：意图服务使用 `INTENT_OLLAMA_*`，未设置时沿用 `OLLAMA_*`；
编排规划器继续使用 `OLLAMA_*`。两端模型客户端和日志分别运行，不共享内存。

意图服务始终返回保留缺参的严格分析结果；调用方再应用当前的参数策略，
避免 Fake 默认值策略影响真实硬件请求。意图服务不可用、超时或返回无效结果时会报错，
不会自动退回单进程识别。可通过 `INTENT_SERVICE_TIMEOUT` 调整跨服务等待时间，
默认至少 180 秒，并在已配置的意图模型超时基础上留出 30 秒。

知识 HTTP 接口使用 `KNOWLEDGE_API_URL` 和 `KNOWLEDGE_API_KEY`；
通用远程智能体使用静态 RPC 地址配置。消息构造和响应解析以对应适配器及其测试为准，
修改接口时同步更新二者。

测试使用 Fake 与模拟模型响应；`test_intent_service.py` 还会启动两个真实 Python 子进程，
验证不同 PID、不同端口以及跨 HTTP 的三条路径和服务故障行为。
这些测试不代表已验证真实 Ollama 或物理硬件的端到端行为。
日常文档只维护本路线和 README；旧材料保存在 `archive/` 中，用于需要时追溯。
