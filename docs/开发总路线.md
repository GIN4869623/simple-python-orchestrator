# 简单编排智能体代码阅读与后续开发路线

## 当前版本做了什么

当前代码实现一条由本地 LLM 规划、由编排器确定性执行的流程。能力注册表和严格计划校验的代码暂时保留，但默认关闭：

```text
用户请求
  → Ollama 生成结构化意图分析
  → Ollama 生成结构化计划
  → 知识接口 Fake
  → 设备管理接口 Fake
  → USRP 硬件接口 Fake
  → Ollama 评估 Fake 返回并决定继续、重试、重规划、完成或停止
  → 汇总工作流结果
```

知识与设备管理智能体只有一个接口，没有实现其内部功能。设备管理智能体查询网络中的设备信息、状态与能力。USRP 智能体只负责真实 USRP 硬件操作，当前可直接接收任务，不强制依赖 `device.select` 或 `device_id`。需要研究能力匹配与严格校验时，可以显式启用能力注册表。

## 第一轮：按顺序阅读代码

### 1. 先读 `models.py`

重点看：

- `TaskStatus`：一个任务执行到哪一步。
- `ResultStatus`：一次接口调用返回什么结果。
- `WorkflowStatus`：整个工作流最终怎样结束。
- `Task`：任务描述和依赖。
- `IntentAnalysis`：与智能体无关的结构化业务意图。
- `TaskPlan`：规划状态、意图分析和可执行任务。
- `AgentResult`：专业智能体的统一返回值。
- `WorkflowState`：一次编排运行的全部状态。

阅读后应能解释：为什么 `failed`、`rejected` 和 `unknown` 不能合并成一个状态。

### 2. 再读 `agent_registry.py` 和 `validation.py`

- `AgentRegistry`：保存智能体能力、支持目标、前置条件和排除项。
- `PlanValidator`：用普通 Python 代码阻止越界计划。

这两部分当前默认禁用；使用 `--enable-agent-registry` 时才参与规划。重点理解：LLM 负责理解和规划，注册表与校验器启用后负责确定智能体资格。

### 3. 再读 `ports.py`

这里只定义编排器依赖什么：

- `KnowledgeAgentPort.invoke()`：知识智能体唯一接口。
- `DeviceManagerPort.invoke()`：设备管理智能体唯一接口。
- `UsrpAgentPort.execute()`：USRP 硬件接口。

重点理解 Protocol：Orchestrator 面向接口，不依赖具体实现。

### 4. 再读 `planner.py`

这里提供两种规划器：

- `FixedPlanner`：使用确定性规则生成意图和计划，供离线运行与测试。
- `OllamaPlanner`：先调用本地 Ollama 分析意图，再把当前可用的智能体 ID 交给模型规划；显式开启能力注册表时才查询候选智能体资料。

重点理解：LLM 负责生成 `Task`，并在每个 Fake 返回后生成结构化 `ReviewDecision`，但不直接执行任务。Ollama 的服务地址、模型名和超时由 `.env` 或命令行参数配置。

### 5. 再读 `fakes.py`

三个 Fake 提供确定性结果：

- Fake Knowledge 可以成功或失败。
- Fake DeviceManager 可以提供并选中设备、报告无设备可用或返回未知。
- Fake USRP 可以成功、失败或返回未知，并记录调用次数。

重点理解：Fake 不是另一个真实智能体，而是让编排逻辑不依赖模型、网络和硬件也能测试。

### 6. 重点读 `orchestrator.py`

建议按以下调用链阅读：

```text
run()
  → planner.create_plan()（内部先分析意图，再生成任务计划）
  → _dependencies_succeeded()
  → _execute()
  → planner.review()
  → _task_status_for()
  → _stop_workflow() 或 _build_final_answer()
```

阅读时逐行追踪两个场景：

1. 全部成功时，状态怎样从 pending 变为 succeeded。
2. 开启能力注册表后，没有可用设备时，为什么 UsrpAgent 不会被调用。
3. LLM 只返回 knowledge 任务时，为什么另外两个执行器不会被调用。

### 7. 再读 `main.py`

它只负责命令行参数、依赖组装、调用 Orchestrator 和打印结果。业务判断不应该放在入口文件中。

### 8. 最后读测试

测试覆盖：

- 全流程成功。
- 知识接口失败后停止。
- 设备选择失败后不调用 USRP。
- USRP 状态未知时不伪装成成功。
- Fake 演示允许模糊 USRP 请求并记录默认补全参数。
- 严格模式下参数不完整的 USRP 请求会留在终端继续询问。
- RIS 等非 USRP 硬件请求不会进入 USRP 智能体。

参数处理分为两种策略：当前 Fake 演示默认使用 `demo_defaults`，允许后端补全缺失
参数；真实 USRP 必须使用 `strict`，缺参时由终端继续询问并重新分析。

先预测每个测试的执行路径，再运行测试验证自己的理解。

## 第二轮：动手做小修改

读懂后不要立即加 LangGraph。建议依次做四个小练习：

1. 给 `AgentResult` 增加 `error_type`，同步修改 Fake 和测试。
2. 给每个任务记录开始和结束时间。
3. 增加一个 USRP 失败场景测试。
4. 在命令行中增加 `--knowledge-fail`，观察下游任务是否被跳过。

每次只改一个点并运行全部测试。

## 第三轮：接入实际 USRP 硬件智能体

先新增 `UsrpAgentAdapter`，保持 Knowledge 和 DeviceManager 两个 Fake 不变：

1. 接健康检查或 dry-run。
2. 接 operation ID 和状态查询。
3. 接取消操作。
4. 最后才允许真实副作用。

不要把 USRP 智能体的内部 Skill、ToolRegistry 或 LangGraph 复制到 Orchestrator。

## 后续功能顺序

固定闭环稳定后，再按需要逐项增加：

1. 更完整的计划与重规划校验。
2. 超时和错误分类。
3. operation ID 与幂等。
4. checkpoint 和恢复。
5. 人工审批与取消。
6. 只读任务并发。
7. LangGraph 迁移。
8. 日志、指标和评测集。

知识与设备管理智能体始终只保留接口；它们的内部实现不进入本项目。

## 运行方式

```bash
cd ~/Desktop/simple-python-orchestrator
export OLLAMA_MODEL="<你的本地模型名>"
PYTHONPATH=src python3 -m simple_orchestrator.main "解释 QPSK 原理"
PYTHONPATH=src python3 -m simple_orchestrator.main "查询网络中有哪些可用设备" --planner fixed
PYTHONPATH=src python3 -m unittest discover -s tests -v
```
