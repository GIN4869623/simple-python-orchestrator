# 远程业务任务消息契约（v1.0）

本文定义通用 JSON-RPC 适配器的消息格式。已接入的真实知识问答接口使用普通 HTTP JSON，
其请求字段与响应映射见[知识智能体接入](知识智能体接入.md)，不使用本文的 JSON-RPC 包装。

主编排器通过 HTTP 或 TCP + JSON-RPC 2.0 的 `tasks.send`，把一个**业务任务**委派给固定配置的专业智能体。远端自行规划内部步骤、选择工具并执行；目标智能体由可信静态地址选定。内部能力标签用于能力匹配和边界校验，不指定远端必须调用哪个工具。若只是需要调用远端暴露的工具读取参数，可以另用 MCP；MCP 工具调用不代替这里的任务委派契约。

## 请求

### 知识与网络监管智能体

发给 `knowledge` 和 `device_manager` 的业务任务只包含自然语言 `message`。
知识问答只发送一个问题：单个问答任务使用用户原问题；拆分子任务使用 `inputs.question`
或子任务描述，仅附加必要条件和依赖结果。预期输出和验收标准留在编排器内部，不拼入知识问题。
网络监管任务仍合并任务目标、用户需求、已知条件、预期结果和验收条件，以及必要上下文。
嵌套参数转换成可读文字。

编排器在调用专业智能体前统一转换，Fake 本地接口和远程适配器都接收同样的
`{"message": "一段自然语言任务说明"}`。请求、任务、尝试编号通过独立的 `metadata`
参数传给适配器和日志模块，不混入业务输入。远程传输的 `params` 也只含 `message`：

```json
{
  "jsonrpc": "2.0",
  "id": "req-123:D1:1",
  "method": "tasks.send",
  "params": {
    "message": "请查询当前可用的 USRP 设备，列出设备编号、型号、在线状态和连接状态，只读取信息，不执行硬件操作。"
  }
}
```

此格式同时适用于 HTTP 和 TCP。远端从 `params.message` 读取任务，请求的 `id`
格式为 `request_id:task_id:attempt`，例如上面的任务编号为 `D1`。响应原样带回 `id`，
并在 `result.task_id` 中返回任务编号。编排器的规划、依赖调度和结果校验继续使用内部结构化数据。

### USRP 智能体

USRP 保留结构化业务任务格式：

```json
{
  "jsonrpc": "2.0",
  "id": "req-123:T2:1",
  "method": "tasks.send",
  "params": {
    "contract_version": "1.0",
    "request_id": "req-123",
    "task_id": "T2",
    "attempt_id": "req-123:T2:1",
    "source": "orchestrator",
    "target": "usrp",
    "task": {
      "goal": "在选定设备上按用户参数发射 QPSK 信号 5 秒",
      "inputs": {
        "waveform": "QPSK",
        "duration_seconds": 5,
        "device_candidates_from": "D1.network_devices"
      },
      "expected_output": ["操作结果", "实际配置"],
      "completion_criteria": ["报告操作是否完成及实际参数"],
      "routing_capability": "usrp.transmit"
    },
    "context": {
      "user_request": "使用 USRP 发射 QPSK 信号 5 秒",
      "dependency_results": {
        "D1": {"network_devices": [{"device_id": "USRP-01", "device_type": "usrp", "status": "online"}]},
        "K1": {"skill_id": "usrp-operation", "version": "1"}
      },
      "skill_ref": {"skill_id": "usrp-operation", "version": "1", "sha256": "..."},
      "selected_device": {"device_id": "USRP-01"}
    }
  }
}
```

`id` 和 `attempt_id` 标识本次尝试；同一业务任务重试时 `task_id` 保持不变，`attempt_id` 改变。`target` 由可信静态配置选路，Planner 不指定 URL。`task.goal`、`inputs`、`expected_output`、`completion_criteria` 分别描述目标、已知输入、预期产物和验收条件。`context.dependency_results` 只包含当前任务依赖的成功结果；`skill_ref` 和 `selected_device` 仅在对应前置任务通过校验后出现。远端不能把 `context` 当作操作授权，仍需自行校验权限、Skill 和设备状态。

`MainState` 中的完整计划历史、重试次数、批次评审、其他无关任务结果都不进入消息。图内的 `Send` 只把分支上下文交给适配节点；适配节点再生成上面的网络消息。

## 响应

远端完成后返回当前同步契约的最终结果：

```json
{
  "jsonrpc": "2.0",
  "id": "req-123:T2:1",
  "result": {
    "task_id": "T2",
    "status": "succeeded",
    "summary": "信号发射完成",
    "data": {"operation_id": "op-42", "actual_configuration": {}},
    "error": null
  }
}
```

业务状态目前为 `succeeded`、`failed`、`rejected` 或 `unknown`。JSON-RPC `error` 表示协议或服务调用错误；业务执行失败应放在 `result.status` 中。主编排器核对响应 `id`、`task_id` 和状态，然后把结果写入自己的 State。远端内部计划与工具轨迹由远端管理，不作为主图 State 的一部分。

网络监管只负责只读查询，支持 `device.list`、`device.inspect`，不选择、占用或使用设备。
成功响应的 `data` 只有 `network_devices`，其中每台设备包含 `device_id`、`device_type`、
`status`。不返回 `selection`、`selected_device` 或 `capabilities`。
硬件任务使用的目标设备由编排器从查询结果中确定，写入交给 USRP 的内部上下文。
Fake 的能力信息保留在本地设备记录中供前置校验读取，不写入返回报文。

这一版仍是同步请求，必须在配置的超时内返回最终结果。长时间任务将来需要提交确认、状态查询和取消等额外方法；当前代码尚未实现。

## 收发记录

CLI 将 `knowledge`、`device_manager` 的完整请求与响应消息体逐条追加至
`logs/agent_messages.jsonl`；USRP 暂不记录。可用 `--agent-log-path` 或
`ORCHESTRATOR_AGENT_LOG_PATH` 指定路径。

每条记录含 `timestamp`、`agent_id`、`transport`、`request_id`、`task_id`、`attempt_id`
及 `event`（`request`、`response`、`error`）。完整 JSON 消息放在 `payload` 中，
原始消息文本放在 `raw_body` 中；非 UTF-8 响应使用 `raw_body_base64`。
响应在 JSON 解析和关联校验之前记录，因此非法 JSON、错误的响应编号、HTTP 错误响应也可追查。
连接失败或超时时记录异常，不能把调用前写入的请求记录视为远端已接收的证明。

HTTP 认证头不写入日志。TCP 的 `raw_body` 为四字节长度头之后的完整消息体。
Fake 模式以 `transport: "fake"` 记录实际本地接口输入和返回对象，不作为网络报文。
