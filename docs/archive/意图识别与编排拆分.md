# 意图识别与任务编排拆分

更新日期：2026-11-16。

意图识别是请求入口，动态编排是按需调用的能力。步骤清楚的业务直接调用专业智能体，
或者执行已经定义的业务流程，无需让模型额外生成计划和决定下一步。

## 当前调用链

```text
CLI / HTTP
    → RequestRouter
    → IntentAgent：理解请求、识别缺参、建议 handling_mode
        ├─ unsupported：返回不支持
        ├─ needs_clarification：返回补充问题，暂不规划或执行
        ├─ direct：绑定一个明确的业务调用 → WorkflowExecutor
        ├─ fixed_workflow：装配预定义业务流程 → WorkflowExecutor
        └─ orchestrated：GraphOrchestrator → Planner 规划、调度、结果复盘与重规划
```

| 路径 | 当前适用业务 | 模型调用 |
| --- | --- | --- |
| `direct` | 通信知识问答、设备清单和状态查询、USRP 专属只读知识问答 | 仅意图识别；之后直接调用业务智能体 |
| `fixed_workflow` | 单一 USRP 操作，先完成 Skill 和设备查询，再执行硬件任务 | 仅意图识别；流程定义、调度与状态处理由代码完成 |
| `orchestrated` | 需要动态拆解、协调或根据中间结果调整任务的请求 | 意图识别一次，再调用规划和批次复盘；按需重规划 |

这里的模型调用次数只统计本项目的控制流程。专业智能体内部是否调用模型，由各自实现决定。
`--planner fixed` 使用离线规则识别意图，并以 FixedPlanner 演示动态路径，不调用模型。
离线规则只识别已有演示业务和少量明确的多步骤表达，不能代替通用业务理解。

## 组件边界

- `intent_agent.py`：独立的 `IntentAgentPort` 实现、提示词、JSON Schema、参数策略和澄清问题。
  输出 `IntentAnalysis`，其中 `handling_mode` 是建议处理路径，不输出 Task 或执行请求。
- `router.py`：应用入口。先处理澄清和不支持，再匹配允许直接调用的处理器或已有固定流程。
  建议路径没有匹配的处理器、没有覆盖全部所需能力时，转入动态编排；不会丢弃剩余能力。
- `workflows.py`：直接业务调用的静态映射与已有固定流程定义。当前只有单一 USRP 操作的固定流程；
  其他领域要先添加明确的流程定义，才能使用固定路径。
- `planner.py`：动态任务规划及执行复盘。`GraphPlannerPort` 不再要求意图识别方法。
- `graph_orchestrator.py`：接收上游意图，驱动动态规划、执行、复盘和重规划。
- `execution.py`：三条路径共用的任务执行层，包含依赖调度、适配器调用、结果记录、
  设备及 Skill 前置检查、有限重试和状态汇总。直接和固定路径不持有 Planner，也不调用模型复盘。
- `ollama.py`：无会话记忆的模型连接客户端。默认两个智能体共用一个客户端，
  使用原有 `OLLAMA_*` 配置；每次请求单独发送各自的提示词和上下文，不共享对话历史。

直接路径也使用 Task 作为内部调用记录，保留现有日志和响应格式；这不表示调用了动态任务规划。
直接和固定路径按业务智能体的结构化结果判断执行状态，内容正确性由业务智能体负责，
不额外运行 LLM 语义评估。失败按 `max_retries` 有限重试；耗尽后停止，不自动生成新流程。
需要替代策略或动态重规划的请求应走 `orchestrated`。

## Agent Registry 后续接入

本次没有建立新的能力仓库服务，也没有加载 `agents/` 下的 JSON。
默认继续关闭旧的本地注册表，使用显式配置的适配器与业务能力映射。
`--enable-agent-registry` 仍可启用已有的能力匹配与计划校验；固定流程匹配时会包含其设备查询前置能力。
后续可以在意图识别之后、路径与执行目标选择之前接入能力仓库，替换静态映射。
现有注册表只是能力描述，不提供在线状态、发现服务或动态节点注册。

硬件执行继续要求用户明确指定 USRP，且必须完成原有 Skill 和设备检查。
即使模型建议 `direct`，单一硬件操作也会走完整固定流程。
远程物理执行仍默认拒绝，物理结果为 `unknown` 时不会自动重试。
本次没有扩展原有硬件类型和业务能力范围。

## CLI 与 HTTP

启动命令及 `.env` 无需调整。CLI 会显示“直接调用”“固定流程”，动态路径继续显示规划结果。
HTTP 的提交、查询和认证方式不变，保留 `plan_history`、`results`、`reviews` 等字段，新增：

- `intent.handling_mode`：意图识别建议的路径。
- `handling_mode`：实际采用的路径，值为 `direct`、`fixed_workflow` 或 `orchestrated`。
- `clarification_questions`：需要补充信息时返回的问题列表。

直接和固定路径的 `reviews` 是代码根据执行状态产生的判断，不是模型复盘。
缺参时仍然通过补充原请求并重新提交完成澄清，HTTP 尚未增加会话存储或 checkpoint 恢复。

原来的 `Planner.analyze_intent()`、`create_plan()` 和不传上游意图的 `GraphOrchestrator.run()`
保留为兼容入口，供旧串行示例和直接调用者使用；CLI / HTTP 已使用新的独立意图识别入口。
旧结构化数据若没有 `handling_mode`，保守按 `orchestrated` 处理；新意图模型的 Schema 要求输出此字段。
